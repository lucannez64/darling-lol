# Security fixtures

Two tiers, for two different questions.

## Tier 1 — synthetic fixtures (generated on Linux, no Mac)

Generated with [`rcodesign`](https://github.com/indygreg/apple-platform-rs)
(apple-codesign), which is an independent implementation of Apple's code
signing format. These fixtures test the **parser and cdhash math**, not Apple's
policy.

```sh
# ad-hoc (no identity)
rcodesign sign --binary-identifier com.example.adhoc input.dylib adhoc.dylib

# self-signed, Developer-ID-shaped, with a team name
rcodesign generate-self-signed-certificate \
    --person-name "Darling Test" --pem-filename testcert
rcodesign sign \
    --pem-source testcert.crt --pem-source testcert.key \
    --team-name DARLINGTEST --binary-identifier com.example.devid \
    input.dylib devid.dylib

# independent cdhash reference
rcodesign compute-code-hashes devid.dylib
rcodesign print-signature-info devid.dylib
```

Rules:

- Fixtures are **generated by the test** into a temp dir, never committed.
- `rcodesign` itself warns that self-signed output "varies from Apple's
  tooling". That is fine for parser tests and explicitly **not** evidence of
  Apple policy acceptance.
- Cross-check every cdhash against `rcodesign compute-code-hashes`; a mismatch
  is a bug in `dc_codesign`, not in the fixture.

## Tier 2 — real Apple fixtures (external, fetched at test time)

Real Developer ID / notarized binaries come from public releases (for example
Firefox, VS Code, OBS). They are **not vendored**. The test fetches a pinned
URL, verifies a pinned SHA-256, and uses the `.app` only as a read-only vector.

```json
// fixtures/external.json (example shape)
{
  "vectors": [
    {
      "name": "firefox-notarized",
      "url": "https://...",
      "sha256": "...",
      "kind": "developer-id+notarized"
    }
  ]
}
```

These answer "does a real Apple-signed image parse and page-verify?" without
redistributing Apple-signed software. They do **not** yet verify CMS chains,
Developer ID chain trust, notarization tickets, or Apple policy; those remain
unverified until `dc_verify_cms()` and a real trust/ticket check exist.

## Tier 3 — behavioural ground truth (real macOS, via CI)

`tests/security/probe/ground_truth.c` is a read-only probe of `csops`, `csrctl`
and the running task's signing state. `.github/workflows/security-ground-truth.yml`
runs it on GitHub's arm64 macOS runners (Intel hosts can run it manually) and uploads JSON artifacts.

This is the only tier that can answer "what does macOS actually return?".
It requires no Apple hardware ownership: a public repository gets free macOS
runner minutes, and the probe never signs, writes or launches a game.

```sh
# locally, on any Mac
clang -O2 -Wall -Wextra -o ground_truth tests/security/probe/ground_truth.c
./ground_truth > ground-truth.json
```

Artifacts feed `docs/security/GROUND_TRUTH.md` (provenance, macOS version,
runner image, date) and are diffed across versions.

After downloading a run:

```sh
python3 tests/security/ground_truth_to_golden.py ARTIFACT_DIR \
    --json tests/security/fixtures/macos-golden.json \
    --markdown docs/security/GROUND_TRUTH.md \
    --run-id <id> --date <YYYY-MM-DD>
```

The probe's own cdhash changes per build, so the golden file records its
**flags**, not its hash. Apple binary cdhashes are recorded per macOS build.

## What each tier proves

| Question | Tier |
|---|---|
| SuperBlob/CodeDirectory parsing, cdhash, special slots | 1 |
| Real Apple/Developer ID binary parsing and page hashes | 2 |
| Developer ID chain trust, notarization tickets, Apple policy | not verified |
| `csops`/`csrctl` semantics, flags, cross-process behaviour | 3 |
| SIP path enforcement | 3 + runtime tests |
